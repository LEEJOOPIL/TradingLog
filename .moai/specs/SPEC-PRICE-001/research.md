# SPEC-PRICE-001 — 사전 조사

아키텍처 범위는 이미 확정되어 있으므로, 이 문서는 **바이낸스 API 응답 형식과 오류 모드**에 집중한다.

## 1. 엔드포인트

```
GET https://api.binance.com/api/v3/ticker/price?symbol=<SYMBOL>
```

- 인증 불필요(공개 시장 데이터). API 키·서명 없음.
- 요청 가중치(weight) 1 — `symbol` 파라미터를 생략하면 전 종목이 반환되며 가중치가 크게 올라간다. **항상 `symbol`을 명시한다.**

## 2. 실측 응답 (2026-08-23 확인)

아래는 실제 엔드포인트를 호출해 관찰한 출력이다(추정 아님).

### 2.1 성공

```
$ curl -s -w "\nHTTP:%{http_code}\n" "https://api.binance.com/api/v3/ticker/price?symbol=BTCUSDT"
{"symbol":"BTCUSDT","price":"76258.01000000"}
HTTP:200
```

**핵심**: `price`는 **숫자가 아니라 문자열**이다. 반드시 `parseFloat()` 변환이 필요하고, 변환 결과가 `NaN`이거나 유한하지 않으면 오류로 처리해야 한다.

### 2.2 잘못된 심볼

```
$ curl -s -w "\nHTTP:%{http_code}\n" "https://api.binance.com/api/v3/ticker/price?symbol=NOSUCHPAIR"
{"code":-1121,"msg":"Invalid symbol."}
HTTP:400
```

- HTTP 400 + `{code:-1121, msg:"Invalid symbol."}`
- 상장폐지된 심볼도 동일하게 이 형태로 응답한다.

### 2.3 기본 7종 자산 심볼 가용성 (실측)

| 자산 | 후보 심볼 | 실측 결과 |
|------|-----------|-----------|
| 비트코인 | `BTCUSDT` | 200 / `76258.01000000` |
| 이더리움 | `ETHUSDT` | 200 / `2387.61000000` |
| 솔라나 | `SOLUSDT` | 200 / `92.25000000` |
| 금 | `XAUUSDT` | **400 / Invalid symbol** — 현물 금 페어 없음 |
| 은 | (후보 없음) | 현물 은 페어 없음 |
| USDT | (후보 없음) | USDT가 기준통화 자체 — `USDTUSDT` 미존재 |
| USDC | `USDCUSDT` | 200 / `1.00006000` (참고용, 사실상 1.0 고정) |

→ 사용자가 확정한 "금·은·USDT·USDC는 심볼 공란" 방침과 실측이 일치한다. `PAXGUSDT`(토큰화 금, 실측 200 / `4587.42000000`)가 존재하지만 **현물 금 온스 시세가 아니라 별도 자산**이므로 기본값으로 넣지 않는다. 원한다면 사용자가 직접 등록할 수 있다(데이터 주도 설계의 이점).

### 2.4 공개 데이터 미러 호스트

```
$ curl -s -w "\nHTTP:%{http_code}\n" "https://data-api.binance.vision/api/v3/ticker/price?symbol=BTCUSDT"
{"symbol":"BTCUSDT","price":"76226.48000000"}
HTTP:200
```

`data-api.binance.vision`은 동일 경로·동일 응답 형식의 공개 시장 데이터 전용 미러다. 이번 SPEC은 `api.binance.com` 단일 호스트만 사용하고 자동 폴백은 제외 범위로 둔다(spec.md §6). 다만 아래 §3의 지역 차단 위험이 실제로 발생하면 이 호스트가 1순위 대안이 된다 — 그 판단은 별도 SPEC의 몫이다.

## 3. 오류 모드 목록 (구현이 반드시 다뤄야 하는 것)

| # | 오류 모드 | 감지 방법 | 사용자 메시지 방향 |
|---|-----------|-----------|--------------------|
| E1 | 심볼 미등록(빈 값) | 시트 조회 결과가 빈 문자열 | "심볼이 등록되지 않았습니다" |
| E2 | 잘못된/상장폐지 심볼 | HTTP 400 + `code:-1121` | "심볼을 찾을 수 없습니다" |
| E3 | 레이트리밋 | HTTP 429 (`Retry-After` 헤더 동반) | "요청이 많습니다. 잠시 후 다시" |
| E4 | IP 차단 | HTTP 418 | "일시적으로 조회가 차단되었습니다" |
| E5 | 지역 차단 | HTTP 451 | "이 지역에서 조회할 수 없습니다" |
| E6 | 네트워크/타임아웃 | `UrlFetchApp.fetch` 예외 | "네트워크 오류" |
| E7 | JSON 파싱 실패 | `JSON.parse` 예외 | "응답 형식 오류" |
| E8 | 수치 변환 실패 | `parseFloat` 결과가 `NaN`/무한 | "가격 형식 오류" |

E3~E5는 이번 실측에서 재현되지 않았다(정상 200 응답). **미관측 항목이며**, HTTP 상태 코드 분기로 방어적으로 다루되 "실측 확인됨"으로 주장해서는 안 된다.

**E5 관련 주의**: Apps Script 요청은 사용자 브라우저가 아니라 **Google 서버에서 나간다**. 따라서 사용자의 위치가 아니라 Google 이그레스 IP의 위치가 차단 판정 기준이 된다. 로컬에서 `curl`이 성공했다는 사실은 Apps Script에서 성공한다는 보증이 아니다 — 이 검증은 run 단계에서 실제 Apps Script 실행으로 확인해야 한다(acceptance.md AC-009).

## 4. Apps Script 호출 시 주의점

```javascript
const res = UrlFetchApp.fetch(url, {
  muteHttpExceptions: true,   // 비 200에서 예외를 던지지 않게 함
  followRedirects: true
});
const code = res.getResponseCode();   // 상태 코드 직접 분기
```

- `muteHttpExceptions: true`를 **반드시** 지정해야 400/429/451을 `try/catch` 없이 상태 코드로 분기할 수 있다. 지정하지 않으면 비 200 응답이 예외로 던져져 오류 메시지가 뭉개진다.
- `UrlFetchApp`은 Apps Script 일일 쿼터(소비자 계정 기준 하루 20,000 호출대)를 소모한다. 이번 설계는 **사용자가 버튼을 누를 때만** 호출하므로 쿼터 압박이 사실상 없다. 자동 주기 조회를 제외 범위로 둔 이유이기도 하다.
- 웹앱 배포 스크립트가 외부 URL을 호출하려면 `appsscript.json`의 OAuth 스코프에 `https://www.googleapis.com/auth/script.external_request`가 필요하다. 최초 실행 시 재승인 프롬프트가 뜰 수 있다 — 이는 사용자에게 안내해야 하는 배포 절차상의 변화다.

**`initAssetTypesSheet_()`의 조기 반환**이 이 SPEC에서 가장 중요한 기존-코드 사실이다. 기존 사용자의 시트는 이 함수를 다시 호출해도 B열 헤더가 생기지 않으므로, 별도의 멱등 헤더 프로비저닝 경로가 필요하다(REQ-006).

**범위를 벗어난 읽기 관용성**: 신규 시트는 기본 열 개수가 26열이므로 `getRange(2, 1, n, 2)`로 A:B를 읽어도 B열 데이터가 없을 뿐 예외는 나지 않고 빈 문자열이 채워진다. 즉 리더는 헤더 유무와 무관하게 동작한다 — 헤더는 사람이 읽기 위한 것이다. (이 관용성은 문서 근거에 기반한 추론이며, run 단계에서 실제 시트로 확인 필요.)

## 7. 소수 자릿수 — 해소됨 (사용자 결정, 2026-08-23)

### 7.1 결정

**바이낸스에서 가져온 가격은 소수점 둘째 자리까지만 사용한다.** (사용자 확정)

근거:

- 사용자가 "적용"을 누르기 전에 **눈으로 한 번 확인하는 값**이다. 이 용도에는 센트 단위면 충분하다.
- `76258.01000000` 같은 8자리 표시는 시트의 나머지 숫자 서식(`#,##0.######`)과 어긋나 시각적으로 튄다.

이 규칙은 **바이낸스 조회 값에만** 적용된다. 사용자가 직접 타이핑하는 값의 정밀도는 건드리지 않는다(spec.md REQ-025) — 같은 입력 필드를 공유할 뿐 서로 다른 경로다.

### 7.2 구현 방식 실측 — 통념이 틀렸다

"`Math.round(x*100)/100`은 절반 지점에서 틀리니 `Number(x.toFixed(2))`를 쓰라"는 통념이 널리 퍼져 있다. **실측 결과 이 통념은 사실이 아니다.** 아래는 IEEE754 배정밀도에서 두 방식을 정확히 계산한 값이다.

| 입력 | 실제 저장된 이진값 | `Math.round(x*100)/100` | `Number(x.toFixed(2))` |
|------|--------------------|--------------------------|-------------------------|
| `1.005` | 1.00499999999999989… | `1` | `1` |
| `2.675` | 2.67499999999999982… | `2.68` | **`2.67`** |
| `1.115` | 1.11499999999999999… | `1.12` | **`1.11`** |
| `8.005` | 8.00500000000000078… | `8.01` | `8.01` |
| `1234.565` | 1234.56500000000005… | `1234.57` | `1234.57` |
| `76258.01` | 76258.00999999999476… | `76258.01` | `76258.01` |

읽어야 할 사실 세 가지:

1. **`1.005` → `1`은 두 방식 모두에서 발생한다.** `toFixed`는 이 문제를 고치지 못한다. 통념의 전제가 틀렸다.
2. **두 방식이 갈리는 경우가 실제로 있다**(`2.675`, `1.115`). 그리고 그 경우 십진 직관에 가까운 쪽은 오히려 `Math.round` 쪽이다 — 통념과 반대다.
3. 근본 원인은 반올림 방식이 아니라 **십진 리터럴이 이진으로 정확히 표현되지 않는다**는 데 있다. `2.675`는 애초에 2.67499999…로 저장되므로, 어떤 방식도 파싱 시점에 이미 사라진 의도를 복원할 수 없다.

### 7.3 권장 구현

```javascript
const rounded = Number(parseFloat(raw).toFixed(2));
```

선택 이유는 "절반 지점이 정확해서"가 **아니다**(§7.2에서 반증됨). 다음 두 가지 때문이다.

- ECMAScript 명세에 동작이 정의된 단일 연산이라 읽는 사람이 의도를 오해할 여지가 적다.
- `Math.round(x*100)/100`은 큰 값에서 `x*100`이 정밀도 한계에 닿을 수 있으나, `toFixed`는 그 중간 곱셈이 없다.

`Number(...)` 감싸기는 필수다 — `toFixed`는 **문자열**을 반환한다.

**절반 지점의 방향은 규정하지 않는다.** 최대 오차가 0.01 USD이고, 사람이 확인 후 "적용"하는 값이므로 실질적 영향이 없다. acceptance.md의 검증도 특정 방향을 단정하지 않고 "둘째 자리 이하 + 원본과 0.01 미만 차이"만 확인한다(AC-016).

### 7.4 새로 발견된 위험 — 1센트 미만 자산의 0 붕괴

둘째 자리 반올림을 무조건 적용하면 **1센트 미만 가격의 자산이 `0`이 된다.** 실측:

| 심볼 | 실측 가격 | 둘째 자리 반올림 결과 |
|------|-----------|------------------------|
| `SHIBUSDT` | `0.00000530` | **`0`** ← 위험 |
| `PEPEUSDT` | `0.00000390` | **`0`** ← 위험 |
| `DOGEUSDT` | `0.09029000` | `0.09` (정밀도는 잃지만 0은 아님) |
| `ADAUSDT` | `0.21710000` | `0.22` |
| `XRPUSDT` | `1.46250000` | `1.46` |

`0`이 입력 필드에 채워지고 사용자가 "적용"을 누르면 F열이 0이 되고, 수익률 수식 `(현재가 - 매입가) / 매입가 × 100`이 **-100%** 를 낸다. 조용히 잘못된 값을 만드는 경로다.

기본 7종 자산에는 해당 사례가 없지만, 이 SPEC의 심볼 등록은 **데이터 주도**여서 사용자가 언제든 SHIB 같은 자산을 등록할 수 있다. 방치하면 언젠가 반드시 발생한다.

→ spec.md **REQ-024**로 차단 요구사항을 신설했다(반올림 결과가 0인데 원본이 0보다 크면 `{error}` 반환). 다만 **차단 후의 동작**(오류로 끝낼지, 더 높은 정밀도로 예외 허용할지)은 사용자 결정 사항이므로 plan.md §I에 확인 항목으로 올렸다.

### 7.5 §7의 미검증 항목

- 위 표의 값은 IEEE754 배정밀도 연산을 정확히 계산해 얻었으나, **Apps Script(V8 런타임)에서 직접 실행해 확인한 것은 아니다.** Apps Script는 V8이므로 동일한 결과가 나올 것으로 보지만, run 단계에서 실제 실행으로 확인해야 한다(acceptance.md AC-016).
- `SHIBUSDT`/`PEPEUSDT` 가격은 실측이나, 이 자산들을 실제로 등록해 0 붕괴가 재현되는지는 미확인.

### 8.2 결론

1. **Apps Script의 외부 HTTP 요청은 항상 Google 클라우드 서버 IP에서 발신되며, 실제로 클릭한 사용자 기기(데스크톱/모바일)와는 무관하다.** 데스크톱과 모바일에서 서로 다른 결과가 나온 것은 브라우저 차이가 아니라, Apps Script 실행이 매번 Google의 공유 이그레스 IP 풀 중 어떤 IP를 할당받는지가 비결정적이기 때문으로 추정된다.
2. **바이낸스는 이 공유 IP 풀의 일부 대역을 비일관적으로 차단한다.** 동일한 코드·동일한 호스트·동일한 사용자 계정이 어떤 실행에서는 성공(200)하고 다른 실행에서는 지역 차단(451) 또는 접근 거부(403)로 실패했다. 어느 IP 대역이 차단 대상인지, 차단 판정 기준이 무엇인지는 바이낸스 측 정책이므로 이 세션에서 규명할 수 없었다.
3. **호스트를 바꾸거나(미러 전환) 여러 호스트를 순차 시도(듀얼호스트 재시도)하는 것만으로는 근본 해결이 되지 않는다.** 두 대응 모두 "어떤 IP에서 요청이 나가는가"라는 근본 원인을 바꾸지 못하므로, 결국 재현 가능한 실패 사례(Android Chrome 세션)가 남았다.
4. **구조적 해결책은 발신 IP 자체를 사용자 기기로 옮기는 것이다.** 조회 로직을 서버(Apps Script)에서 클라이언트(브라우저 `fetch()`)로 이전하면, 실제 HTTP 요청이 사용자 본인의 네트워크(모바일 데이터 또는 가정용 Wi-Fi)에서 발신되어 Google 클라우드 공유 IP 풀과 그로 인한 차단 문제 자체가 사라진다. 이 SPEC은 이 결론에 따라 spec.md §2.5의 아키텍처 변경을 채택했다.

### 8.3 향후 SPEC을 위한 시사점

- Google Apps Script에서 외부 공개 API를 호출하는 모든 향후 SPEC은, 로컬 `curl` 성공은 물론 **단일 사용자·단일 세션의 Apps Script 성공조차 다른 실행 컨텍스트에서의 성공을 보증하지 않는다**는 점을 전제해야 한다. 위 §3 E5의 경고("로컬 curl 성공은 Apps Script 성공의 보증이 아니다")는 이번 실측으로 한 단계 더 강하게 확장되어야 한다 — "한 Apps Script 실행 컨텍스트에서의 성공도 다른 실행 컨텍스트(다른 기기·다른 세션)의 성공을 보증하지 않는다."
- 사용자가 직접 트리거하는(버튼을 누르는) 대화형 외부 API 호출이면서, 대상 서비스가 클라우드 제공자의 이그레스 IP에 지역/약관 기반 차단 정책을 갖는 경우(바이낸스가 대표적), **서버(Apps Script) 대신 클라이언트(브라우저)에서 직접 호출하는 설계를 사전에 검토할 가치가 있다.** 단, 대상 API가 브라우저의 크로스오리진 요청에 CORS를 허용하는지가 전제 조건이며, 이는 설계 시점에 반드시 확인해야 한다 — 이 SPEC은 사전 검증 없이 진행했고 결과적으로 성공했지만, 이는 검증되지 않은 가정에 기반한 사후 결정이었다(progress.md의 해당 후속 수정 Gaps 참조).
- 403 같은 차단 응답은 대상 서비스의 공식 오류 코드 문서에 명시적으로 나열되지 않을 수 있다. 방어적 코드는 "알려진" 상태 코드 분기만이 아니라, 실제 상태 코드를 오류 메시지에 노출하는 포괄적인 비-200 폴백 분기를 갖춰야 실기 진단이 가능하다.
